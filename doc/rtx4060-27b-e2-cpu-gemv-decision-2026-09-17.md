# RTX 4060 / Qwen3.8-27B：E2（CPU GEMV 混合计算）决策与修正计划

日期：2026-09-17
前置文档：`rtx4060-27b-e2-cpu-gemv-floor-2026-09-17.md`（地板测量）、`rtx4060-27b-offload-speedup-plan-2026-09-16.md`（原 A–E 方案）
微基准：`.workbuddy/tmp/cpu_gemv_bench.cpp`（786 行，AVX2，含三条路径 + fp64 参考）

---

## 0. 结论摘要

| 问题 | 答案 |
|---|---|
| E2 物理前提（CPU 带宽 ≫ PCIe）是否成立 | ✅ 成立，≈5× |
| E2 能否与 MTP 叠乘（原方案 §4 的 4.4 tok/s） | ❌ **不能，已实测证伪** |
| 数值上能否做到引擎 A16 契约 | ✅ 能，`split` 双链 `rel_l2 = 1.97e-05` |
| E2 值不值得做 | ✅ 值得，但收益是 **+33%** 而不是 +115% |
| 有没有更划算的先行项 | ✅ 有：**把 embedding + lm_head 移出显存预算**（+44%，且与 MTP 正交） |

**建议一句话**：不要按原方案直接把 E2 铺成"全量 host linear 上 CPU 并乘 MTP"。改为
**先做 CPU GEMV 内核 → 再把 embedding/lm_head 移出显存（保留 MTP，+44%）→ 最后才把层权重也搬上 CPU（关掉 MTP，再叠到 ≈4.8 tok/s）**。

**原方案被推翻的那一条**：`rtx4060-27b-offload-speedup-plan-2026-09-16.md` §4 的
"E2：全部 host linear 移到 CPU → ≈4.4 tok/s（MTP 同乘）"。前半句方向对，后半句（同乘）不成立。

## 1. 三条路径的实测结果

微基准工作集：24 张量 / 1.274 GB / 2.35 B 参数（q4 down、q4 gate_up、q5 o_proj 各 8 份），
字节/参数比 1.84，与真实 27B 的 q4/q5 混合（16.14 GB / 27 B = 1.67）同量级，可线性外推。

### 1.1 数值正确性（T=1，每张量 32 采样行，对照 fp64 标量参考）

| 路径 | worst `rel_l2` | 判据 | 结论 |
|---|---|---|---|
| `kernel_fp32`（精确 fp32 反量化 + 精确 fp32 激活） | **3.355e-07** | 3.3e-3 | ✅ 通过 |
| `kernel_int8`（激活 int8 单链 per-group） | **5.401e-03** | 3.3e-3 | ❌ **超标 1.6×** |
| `kernel_int8` + `split`（激活 hi/lo 双链，≈15 bit） | **1.972e-05** | 3.3e-3 | ✅ **通过，且余量 167×** |

q4 与 q5 两类张量同时在 1e-07 量级（fp32）/ 1e-05 量级（split），无按位分布偏差。

**理论预测与实测吻合**：单链 int8 的 per-group 量化误差 ≈ `max|x| / (2√3 · 127)`，
即相对误差落在 1e-3 量级 —— 正好压在判据上。这不是"精度不行"，是**理论上就该差一口气**，
而补上那一口气的代价极低（见下）。

### 1.2 带宽与 T 敏感性（20 线程，单位 GB/s）

| T | read-bound（上限） | fp32 | int8 单链 | **int8 split** |
|---|---|---|---|---|
| 1 | 56.18 | 24.90 | 45.41 | 35.40 |
| 2 | 60.32 | 14.03 | 25.83 | 18.44 |
| 3 | 57.61 | 10.64 | 16.36 | 11.26 |
| 4 | 63.73 | 7.55 | 13.45 | 7.91 |
| 6 | 66.42 | 4.96 | 8.18 | 5.75 |
| 8 | 65.00 | 3.89 | 6.38 | 4.42 |

换算成**每 token 毫秒**（才是决策要看的一列）：

| T | fp32 ms/token | int8 单链 ms/token | **split ms/token** |
|---|---|---|---|
| 1 | 51.17 | 28.06 | 35.99 |
| 2 | 45.40 | 24.66 | 34.54 |
| 3 | 39.90 | 25.95 | 37.72 |
| 4 | 42.20 | 23.69 | 40.29 |
| 6 | 42.78 | 25.95 | 36.91 |
| 8 | 40.89 | 24.97 | 35.99 |

GB/s 随 T 单调下滑，但 **ms/token 近似恒定** —— 这是 compute-bound 的签名：
总耗时 = T × 常数，即每多验证一个候选 token，就多付一整份 ALU 时间。

> ⚠️ **读数纪律**：上表测于外部干扰较轻的时段。同一二进制在数小时后复测（`vmware-vmx` 等占用内存带宽），
> read-bound 降到 38–46 GB/s、fp32 降到 14–16 GB/s —— **绝对带宽整体漂移 40–50%，但 T 趋势的形状不变**，
> 且 `worst rel_l2` 完全一致（3.355e-07 / 5.401e-03 / 1.972e-05）。**决策依据是趋势，不是绝对值。**

> **判据（可复用）**：把带宽换算成 ms/token 再看趋势。若稳定 → 纯 ALU 受限，
> 任何"摊薄访存"的机制（speculative decoding / MTP / 更大 batch）都无法在其上线性叠加。

### 1.3 split 双链几乎免费

T=1：单链 45.41 GB/s → split 35.40 GB/s，只降 **-22%**（ms/token 28.06 → 35.99，+28%），
换来 274× 的精度改善（5.4e-3 → 2.0e-5）。**没有任何理由选单链。**

## 2. 决定性证据：E2 与 MTP 不可叠乘

现状（启动器 bench 实测）：decode 1.8–1.9 tok/s、每轮 2.04 token、接受率 35.3% ⇒ **K=3, T=4**。
每轮 ~1000 ms，其中 PCIe 传输占主导。

| 路线 | 每轮时间 | 每轮产出 | tok/s | vs 现状 |
|---|---|---|---|---|
| 现状：PCIe + MTP(K=3) | ~1000 ms | 2.04 | **2.04** | — |
| E2 fp32 + MTP(K=3) | 42.2 × 4 × 10.2 = 1722 ms | 2.04 | 1.18 | ❌ -42% |
| E2 split + MTP(K=3) | 40.3 × 4 × 10.2 = 1644 ms | 2.04 | 1.24 | ❌ -39% |
| E2 split + MTP(K=1) | 34.5 × 2 × 10.2 = 704 ms | ~1.5–1.7 | ~2.2–2.4 | ❌ 持平偏下 |
| **E2 split，关闭 MTP** | 35.99 × 10.2 = **368 ms** | 1.00 | **2.72** | ✅ +33% |
| P0（见 §3）+ MTP(K=3) | 718 ms | 2.04 | **2.84** | ✅ +39% |
| **P0 + E2 split，关闭 MTP** | 368 ms × 0.561 = **207 ms** | 1.00 | **4.84** | ✅ +137% |

（外推比例 13.04 GB / 1.274 GB = 10.2，host 层权重取 13.04 GB = 16.14 − 3.1 embedding/lm_head）

**关键结论**：E2 在**任何 K 下**与 MTP 组合都不如"E2 单独"或"P0 + MTP"。
E2 的正确用法是**用 CPU 的 5× 带宽替代 PCIe，而不是在其上再叠一层摊薄**。

## 3. 新发现：比 E2 更划算的先行项（P0）

### 3.1 PCIe 有效带宽反推

用已交付的两个手动 offload 数据点（无 MTP）反推：

| ratio | GPU 驻留 | 解出 host 字节 | decode | 隐含有效性带宽 |
|---|---|---|---|---|
| 0.9 | 3.99 GiB | 0.9 × 13.04 = 11.74 GB | 0.90 tok/s (1111 ms) | 10.6 GB/s |
| 0.8 | 5.24 GiB | 0.8 × 13.04 = 10.43 GB | 1.00 tok/s (1000 ms) | 10.4 GB/s |

⇒ 端到端有效 PCIe ≈ **10.5 GB/s**（纯传输实测的 13 GB/s 未完全暴露为端到端收益）。
**ratio 每降 0.1 ⇒ host 少 1.30 GB ⇒ 每轮少 ~124 ms ⇒ tok/s +11%~12%。**

### 3.2 P0：把 embedding + lm_head 移出显存预算

已知事实（27B 特有）：embedding + lm_head 为 bf16、**恒驻留、不参与 offload**，合计 **≈3.12 GB**
（vocab 152k × hidden 5120 × 2 B × 2）。8 GB 卡上它占了近 40% 的可用显存，正是 ratio 卡在
0.8 下不去的根因。

把它移出（任选其一）：

| 方案 | 释放显存 | 代价 | 改动量 |
|---|---|---|---|
| a. 移到 host（bf16 保留），CPU 做 lookup + lm_head GEMV | **3.12 GB** | CPU +8.7 ms/token（390 MB q4） | 中（复用 P1 内核） |
| b. 量化到 q4 仍驻留 GPU | 2.34 GB | 需 dequant-lookup kernel | 中 |
| c. 仅 embedding 移到 host，lm_head 留 GPU | 1.56 GB | 最小 | 小 |

**方案 a 的推算**：resident 2.60 → 5.72 GB ⇒ ratio 0.8 → **0.561** ⇒ host 7.32 GB
⇒ 每轮 697 ms ⇒ **2.93 tok/s（+44%）**，且**与 MTP 完全正交**（减少的是字节数，MTP 仍能摊薄）。

> P0 的关键性质：它优化的是"每轮固定成本"，而 MTP 优化的是"每轮产出 token 数"。
> 两者作用在不同维度，因此可以相乘 —— 这正是 E2 缺失的性质。

## 4. 新计划

### Phase 1 —— CPU GEMV 内核落地（E2 核心，已被微基准验证）

| 项 | 内容 |
|---|---|
| 新增 | `src/core/cpu_gemv.{h,cpp}`：RowSplit split-int8 双链 kernel + 扁平抢单线程池 |
| 数值 | 复刻 `.workbuddy/tmp/cpu_gemv_bench.cpp` 的 `kernel_int8(split)`：目标 `rel_l2 < 1e-03` |
| 线程池 | **禁止** `hardware_concurrency()`（6P+8E 上超配会掉一半性能），需实测标定 |
| 准入 | `dispatch_linear`（`linear.cpp`）新增 residency 判据；`ensure_layer` 命中 host 时跳过上传 |
| 禁止 | 不要写"每张量一次栅栏"的调度（实测 read-bound 37→67.8 GB/s 的差别就在这） |

### Phase 2 —— P0：embedding + lm_head 移出显存（优先交付）

复用 Phase 1 内核，把 host 侧 embedding lookup 与 lm_head GEMV 接上，**MTP 保持开启**。
预期 **2.04 → ~2.9 tok/s**，是收益/成本比最高的一步。

### Phase 3 —— 全量 host linear 上 CPU，并关闭 MTP

host 7.32 GB 全部走 CPU，`--spec mtp` 关闭。预期 **~4.8 tok/s**（受 GPU 侧时间上界约束，见 §5）。

### 明确不做

- ❌ E2 + MTP 叠乘（任何 K）—— 已证伪
- ❌ int8 单链激活（数值不达标，而 split 只贵 22% 带宽）

## 5. 未验证的假设与风险

| # | 假设 | 风险 | 验证方式 |
|---|---|---|---|
| 1 | GPU 侧计算（attention + resident 层 + KV）在无 MTP 时不成为新瓶颈 | ⚠️ 中 —— §2 的 4.84 tok/s 只算了 CPU 侧 207 ms，未测 GPU 侧 | Phase 3 前先测 GPU 侧单 token 时间 |
| 2 | host 字节与 PCIe 时间线性（ratio 0.8→0.56 外推） | ⚠️ 中 —— 只反推过 0.8/0.9 两点 | Phase 2 直接实测 |
| 3 | 微基准字节/参数比 1.84 与真实 1.67 的差异在 10% 内 | ✅ 低 | 已按 10.2 比例外推并留了余量 |
| 4 | q8 路径（`byte_coded`）的 `maddubs` 饱和（255×127×2 = 64770 > 32767） | ⚠️ 已知缺陷，但 27B 权重不含 q8 | 若将来用 q8 权重必须先修 |

## 6. 本轮修掉的 4 个真实缺陷（均为静默错误）

| # | 缺陷 | 症状 | 根因 | 修复 |
|---|---|---|---|---|
| 1 | `_mm256_shuffle_epi8` 做 chunk 重排 | q4/q5 全错，`rel_l2 > 1` | shuffle 是 **lane-local**，永远够不到 chunk 2,3,6,7；且只产出一个 ymm（一组 64 元素需要两个） | 换 `unpacklo/unpackhi_epi32` + `permute2x128`，并按 `halves = byte_coded ? 1 : 2` 出两半 |
| 2 | q5 第 5 位在 int8 的 u8 域未取反 | `rel_l2 ≈ 1.9`（负值全变正） | q4 的偏置是**常数 8**（可组尾一次性减掉）；q5 的偏置是 **16·bit4，逐元素**，必须折进码值：`code = n + 16·(1 − bit4)` | 位平面注入时 `^ 0x10` |
| 3 | int8 激活单链精度不足 | `rel_l2 = 5.4e-3`，压线超标 | per-group int8 量化误差理论下限就在 1e-3 量级 | `split`：第二 lane 存残差 `x − hi·step`，步长 `step/256`，只贵 22% 带宽 |
| 4 | 早前"int8 贴带宽上限 59.3 GB/s"的结论 | 决策依据失真 | 该数字是在**缺陷 #1 的 kernel**上测的 —— 越道导致 `maddubs` 只做了一半工作 | 修正后为 45.4 GB/s（单链）/ 35.4（split） |

## 7. 可复用的判据

1. **compute-bound 判据**：把带宽换算成 ms/token；若随 T 恒定 ⇒ ALU 受限，speculative 类机制不可叠乘。
2. **数值契约判据**：单条点积的相对误差无意义（严重抵消），必须用**跨行 relative_l2**（引擎 A16 判据 3.3e-3）。
3. **布局验证判据**：位平面/元素序这类错误**形状全对、只在 `rel_l2` 暴露**，必须用穷举模拟判定，不能凭推理。
4. **线程池判据**：若"上限"远低于理论值（<70%），先怀疑调度结构（每张量栅栏 / 超配），再怀疑硬件。
