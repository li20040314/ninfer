# E2（CPU GEMV 混合计算）地板实测与可行性判定

**日期**：2026-09-17
**前置文档**：`rtx4060-27b-offload-speedup-plan-2026-09-16.md`（§4 提出 E2，预期 ≈4.4 tok/s）
**平台**：i9-13900H（6 P-core + 8 E-core = 14 物理核 / 20 逻辑核）、2×16 GB DDR5-**5200** 双通道（理论峰值 **83.2 GB/s**）、RTX 4060 Laptop 8 GB
**结论**：**E2 的前提（内存带宽 ≫ PCIe）成立，但方案文档"E2 与 MTP 正交相乘、可达 ≈4.4 tok/s"的推论不成立。** 见 §7。

---

## 1. 结论摘要（TL;DR）

| 项 | 实测 | 说明 |
|---|---|---|
| 内存流式读上限 | **63.6 GB/s**（探针，16 线程）<br>**67.8 GB/s**（微基准 read-bound best-of-6） | 独立探针 / 单块 1.376 GB 连续缓冲；≈ 理论峰值的 **76–81%** |
| 单线程流式读 | **17.7–20.1 GB/s** | 同上 |
| PCIe 有效带宽（现状） | ~13 GB/s | 已交付的 offload 通路 |
| **带宽比值** | **≈5.2×** | ✅ E2 物理前提**成立** |
| 精确 fp32 CPU GEMV | **33.6 GB/s**（best-of-6，T=1，20 线程） | = 带宽上限的 **49%**（ALU 受限） |
| 数值正确性 | `rel_l2 = 3.36e-07`（q4 与 q5 同时最优，完全可复现） | ✅ 远优于 A16 判据 3.3e-3 |
| 整数 int8 GEMV | **45.4 GB/s**（单链）/ **35.4 GB/s**（split 双链） | 见 `-decision-` 文档：早前的 59.3 GB/s 是在越道缺陷下测出的虚高值 |

> **读数纪律**：本机外部干扰会把带宽整体压掉 40–70%（同一 kernel 在一次会话内测到 read-bound 22.96 / 42.4 / 48.4 / 60.9 / 66.9 / **67.8** GB/s）。上表的"上限/最优"取**连续 6 次的最优值**，因为那才是机器能力；中位数没有意义。这本身是 §4.5 的核心教训之一。

**判定**：
1. fp32 精确路径**数值与带宽都达标**，但它 **ALU 受限**，且 **每条 token 的 ALU 成本恒定**（总耗时随 T 线性增长）。
2. 因此 **E2 无法与 MTP 相乘**——MTP 的收益恰恰来自"把访存摊薄到多个 token"，而 fp32 的成本不是访存。
3. 定量推演（§7）：**E2+MTP ≈ 1.6 tok/s < 现状 2.04 tok/s（回退）**；E2 单独 ≈ 2.0 tok/s（与现状持平）。
4. **可以**与 MTP 相乘的是"整数点积"路线（实测已贴带宽上限、且对 T 不敏感），但它需要修 2 个 bug 并新增精度方案。

> 这一步的价值：用一次微基准实测，拦下了一条会耗掉大量工期但**产出为零**的管线改造。

## 2. 为什么必须先用微基准量地板

方案文档 §4 给 E2 的预期是 `13 GB ÷ ~30 GB/s ≈ 4.4 tok/s`（MTP 再同乘）。这个数字隐含一个**未被验证的假设**：CPU 侧 GEMV 能跑到 ~30 GB/s 且**瓶颈在访存**。

只要这个假设不成立，整条管线的收益就是零。而验证它只需要一个独立的微基准 —— 不碰引擎、不改 CMake、不碰五层 linear 准入门控。因此本轮**只做微基准**，先拿到判定依据。

**产物**：
- `.workbuddy/tmp/membw_probe.cpp` — 硬件带宽上限探针（148 行，独立于引擎）
- `.workbuddy/tmp/cpu_gemv_bench.cpp` — RowSplit 布局的真实 GEMV 微基准（~800 行）

## 3. 硬件地板：先证明"上限存在"

探针设计要点（每一条都是为了让数字可信）：

| 设计 | 为什么 |
|---|---|
| `VirtualAlloc` 单块 1.376 GB 连续缓冲 | 排除"多块小分配 / TLB / 碎片"造成的假地板 |
| 计时前 `memset` 全缓冲 | 排除缺页中断计入带宽 |
| 每线程一片**互不重叠**的连续区间 | 纯流式，无跨线程伪共享 |
| 栅栏只开一次（`Gate` 自旋 + `join`） | 线程启动成本**不进**计时区间 |
| `sad_epu8` 累加并回传校验和 | 防止编译器把读循环整个优化掉 |
| 重复 N 次取**最小值** | 抗外部干扰 |

结果（`loadu 32B/iter`）：

| 线程 | 1 | 2 | 4 | 6 | 8 | 12 | 16 | 20 |
|---|---|---|---|---|---|---|---|---|
| GB/s | 17.7 | 34.0 | 50.4 | 53.8 | 57.1 | 61.3 | **63.6** | 61.1 |

- 峰值 **63.6 GB/s** = DDR5-5200 双通道理论 83.2 GB/s 的 **76%** —— 对 SIMT 流式读是健康数字。
- 4 线程即达 50 GB/s，**6 线程到 54 GB/s**；再加线程收益很小。
- 单线程 17.7 GB/s（`loadu 64B/iter` 为 20.1）。
- 非临时加载（`stream_load`）无增益 → 普通 `loadu` 已足够。

**这确认了 E2 的物理前提：内存侧 63 GB/s vs PCIe 13 GB/s，约 4.9× 的空间。**

## 4. 真实布局的 GEMV 微基准

### 4.1 布局与解码（与引擎逐字节对齐）

微基准按引擎 `weight_view.cpp:weight_geometry` 的真实 RowSplit 布局合成张量，元素顺序抄自 `q4_rowsplit_storage.cuh` / `q5_rowsplit_storage.cuh`：

```
codes[n*code_row] | align256 | high[n*high_row] | align256 | scales(fp16)[n*scale_row]
padded_k = align(k,128);  groups = padded_k/64 (q4/q5) 或 /32 (q8)
code_row = groups*32;  high_row = groups*8 (仅 q5);  scale_row = groups*2
```

组内 64 元素的字节映射（**引擎契约**）：

| 元素 | 来源 |
|---|---|
| `8c+i` | 码字节 `4c+i` 的**低** 4 位 |
| `8c+4+i` | 码字节 `4c+i` 的**高** 4 位 |
| `8c+i` 的第 5 位 | high 字节 `c` 的 **bit 2i** |
| `8c+4+i` 的第 5 位 | high 字节 `c` 的 **bit 2i+1** |

码值解码：

```
q4: value = (n ^ 8) - 8        n = 存储 nibble
q5: value = (q ^ 16) - 16      q = nibble | (bit4 << 4)   —— 即 5 位有符号
q8: 字节按有符号读
```

**数值契约**：以"权重精确 fp32 反量化 × 激活的 bf16 精确 fp32 值"为基准比 `relative_l2`。
**不能**把激活压成 int8 —— 那会违反 A16 oracle 契约（见 §6.3）。

### 4.2 AVX2 关键技巧：让**激活**去吸收布局

`unpacklo/unpackhi_epi8`（低/高半字节平面交错）在每个 8 元素块内自然产出元素序
`[0,4,1,5,2,6,3,7]`。

于是**每次调用前把激活按同一模式预置换一次**，权重侧就只剩三件廉价操作，且**没有 shuffle、没有栈往返**：

```
q4: v ^= 0x88;  lo = v & 0x0F;  hi = (v >> 4) & 0x0F
    a = unpacklo(lo,hi) - 8 ;  b = unpackhi(lo,hi) - 8
q5: （同上但不减 8）再减去位平面：a -= lane{b16_lo,b16_hi}, b -= lane{b16_hi 高半}
```

`permute_activation` 把 `out[k+i] = x[k + kOrder[i]]`，`kOrder = {0,4,1,5,2,6,3,7}`。

### 4.3 ⚠️ 踩过的坑：位平面必须用**两张表**

q5 的位平面在"元素序"与"交错槽位序"下**不是同一张表**：

| 消费方 | 需要的位序 | 表 |
|---|---|---|
| `kernel_int8`（先把码洗成元素序） | 元素 i 取 bit `[0,2,4,6,1,3,5,7][i]` | `table.element[256][8]` |
| `kernel_fp32`（保留交错槽位） | 槽位 s 取 **bit s** | `table.slot[256][8]` |

用错表的代价是**静默的**：输出形状完全正确，只是第 5 位挂到了隔壁元素上，只在 `rel_l2` 上暴露（实测 **0.76–1.38**，换对表后 **2.9e-07–5.4e-07**）。

**判定方式**：不想凭推理拍脑袋 —— 用 200×8×8 次穷举模拟该向量布局，三种候选表各自数失配数：

```
element-order (2i / 2i+1)    mismatches = 4878
identity (bit s)             mismatches = 0      ← 正确
kOrder (bit kOrder[s])       mismatches = 4738
```

### 4.4 优化：per-group 的 scale 乘法提到组尾

scale 在一整组内是常量，原来每个 chunk（8 元素）乘一次，共 8 次；改为对组内部分和乘 1 次：

```cpp
__m256 gacc = _mm256_setzero_ps();
for (c : chunks) gacc = _mm256_fmadd_ps(cvtepi32_ps(cvtepi8_epi32(chunks[c])), loadu(xg + c*8), gacc);
acc = _mm256_fmadd_ps(gacc, scale, acc);
```

**同时降低了数值误差**（整数权重精确进入 FMA，rounding 从 8 次降到 1 次）：

| | T=1 带宽 | worst `rel_l2` |
|---|---|---|
| 改前 | 24.95 GB/s | 8.666e-07 |
| 改后 | **29.59 GB/s** | **3.355e-07** |

（同会话 A/B，故可比；机器完全安静时改后可达 **33.61 GB/s**，见 §5。）

### 4.5 ⚠️ 踩过的坑：线程池结构把数字压掉一半以上

第一版按"每张量一次 `Team::run`"组织（24 张量 = 24 次完整栅栏）。在 i9-13900H 上这测的是**线程池**而不是 kernel：

- 每次 `run` 是完整栅栏 → 该张量的进度由**最慢的那个线程**决定；E 核流式带宽约为 P 核的 1/3，于是 6 个 P 核每次都在等 E 核；
- 每次栅栏要对 19 个 worker 做 mutex/CV 唤醒；
- 20 逻辑线程挤 14 物理核，被抢占时其余线程在栅栏上空等一个调度量级。

**改法**（也是正式实现该有的形状）：整个 pass 切成 1232 个约 1 MB 的工作项，线程从**一个原子计数器抢单**，全程**只一次栅栏**。慢线程只是抢得少，不再拖累别人。

| | read-bound | fp32 exact T=1 |
|---|---|---|
| 每张量一次栅栏（20t） | 37–38 GB/s | 11.9 GB/s |
| 扁平抢单（20t） | **64–66 GB/s** | **29.6 GB/s** |

> 附带教训：这台机器上**外部干扰会把带宽整体压掉 40–70%**（曾观测到 read-bound 从 64 掉到 20 GB/s）。因此所有数字都必须**探针/微基准交替、连续背靠背**测，不能跨时段比较。`vmware-vmx`、`ollama`、多个 `WorkBuddy` 进程都在跑。

## 5. 正确性与带宽：最终实测

20 线程、扁平调度、scale 已提升（安静窗口的最优值）：

| T | read-bound | **fp32 exact** | int8 maddubs |
|---|---|---|---|
| 1 | **67.8 GB/s**（18.8 ms） | **33.61 GB/s（38.0 ms）** | 59.3 GB/s（21.5 ms） |
| 4 | 65.4 GB/s（19.5 ms） | 8.12 GB/s（**156.83 ms**） | 21.2 GB/s（60.0 ms） |

连续 6 次测得的分布（说明噪声幅度，取最优为能力值）：

```
run1  read=67.78 GB/s   fp32=32.97 GB/s
run2  read=67.23 GB/s   fp32=32.34 GB/s
run3  read=65.19 GB/s   fp32=30.20 GB/s
run4  read=51.62 GB/s   fp32=26.55 GB/s   <- 外部干扰
run5  read=66.62 GB/s   fp32=27.89 GB/s
run6  read=66.36 GB/s   fp32=33.61 GB/s   <- 最优
```

正确性（32 采样行/张量 vs fp64 标量参考）**完全可复现**（带宽会漂，数值不漂）：

```
down_q4[0]      k=17408 groups=272  rel_l2 fp32=2.576e-07   <-- q4
o_proj_q5[0]    k= 5120 groups= 80  rel_l2 fp32=2.123e-07   <-- q5
o_proj_q5[7]    k= 5120 groups= 80  rel_l2 fp32=1.446e-07   <-- q5
worst rel_l2 over all tensors: fp32=3.355e-07   int8=1.953e+00
```

- **q4 与 q5 同时达到 1e-07 量级** → 精确 fp32 路径**通过** A16 契约。
- 14 线程（=物理核数）时 fp32 = 23.89 GB/s、read-bound = 64.72 GB/s；20 线程更优。

## 6. 关键发现：fp32 是 ALU 受限，因此**不能与 MTP 相乘**

### 6.1 T 扫描：ms/token 恒定

| T | fp32 总耗时 | **ms / token** |
|---|---|---|
| 1 | 43.05 ms | 43.05 |
| 4 | 156.83 ms | **39.21** |
| 8（含噪） | 655.99 ms | **82.00** |
| 6（含噪） | 496.58 ms | **82.76** |

**每 token 的耗时基本恒定**（同一时段内），即 **总耗时随 T 线性增长**。

这正是 compute-bound 的签名：访存在 T=1 时读一次，T=4 时**同一批权重的 ALU 工作量 ×4**，而访存字节不变。

### 6.2 为什么这会推翻"MTP × E2"

MTP（已在 F1 交付，×2.22）的收益机制是 **把一次权重访存摊到多个候选 token 上**：

```
现状（PCIe）:  13 GB ÷ 13 GB/s = 1000 ms / round，2.04 tok/round → 2.04 tok/s   ✅ 与实测 1.8–1.9 吻合
```

MTP 之所以有效，是因为那条路**瓶颈在访存**。而 fp32 的瓶颈是 **ALU**，且 ALU 成本随 T 线性增长 ——
**MTP 摊薄的东西，恰好不是 fp32 的瓶颈。两者不可相乘。**

### 6.3 顺带发现：int8 参考实现有 2 个真 bug（"int8 精度不行"的旧结论无效）

微基准的 int8 路径 `rel_l2 ≈ 1.0–2.0`，**q4 也一样坏**。但 q4 的 int8 理论上只该有 ~1e-2 量级误差 —— 说明这不是精度问题，是 bug：

1. **洗牌重排越道**：`shuf_a`/`shuf_b` 用 `_mm256_shuffle_epi8` —— 该指令**按 128 位道独立**，永远够不到 chunk 2,3,6,7；而且一组 64 个元素只产出了一个 ymm（需要两个）。结果是把 chunk 4,5 的数据放到了元素 16..47 的位置。修复：`unpacklo/unpackhi_epi32` + `permute2x128`，并按 `halves = byte_coded ? 1 : 2` 出两半。
2. **q5 第 5 位未在 u8 域取反**：q4 的偏置是**常数 8**（可在组尾一次性修正）；q5 的偏置是 **16·bit4，逐元素**，在 int8 需要的无符号域里必须折进码值 —— `code = n + 16·(1 − bit4)`。不取反会让每个负值变正（`rel_l2 ≈ 1.9`）。

> ✅ **本节两处结论已在 2026-09-17 上午修正并实测**（详见 `rtx4060-27b-e2-cpu-gemv-decision-2026-09-17.md`）：
> 单链 int8 = `rel_l2 5.401e-03`（压线超标）/ 45.4 GB/s；`split` 双链 = `1.972e-05`（达标）/ 35.4 GB/s。
> 因此 **"int8 已贴带宽上限 59.3 GB/s" 是假结论** —— 它是在只做了一半 `maddubs` 的越道内核上测出来的。

## 7. 定量推演：三条路线对比（真实 27B，host 权重 ≈13 GB）

微基准工作集 1.274 GB ⇒ 缩放 **×10.2**。MTP 的 K=3 / T=4 由启动器 bench 反推（接受率 35.3%、2.04 tok/round）。
下表为 2026-09-17 上午的**实测**结果（详见 `rtx4060-27b-e2-cpu-gemv-decision-2026-09-17.md` §2）：

| 路线 | 每 round 耗时 | tok/round | **tok/s** | vs 现状 |
|---|---|---|---|---|
| 现状：PCIe offload + MTP(K=3) | ~1000 ms | 2.04 | **2.04** | 基准（实测 1.8–1.9） |
| E2 fp32 + MTP(K=3) | 42.2×4×10.2 = 1722 ms | 2.04 | **1.18** | ❌ 回退 |
| E2 split + MTP(K=3) | 40.3×4×10.2 = 1644 ms | 2.04 | **1.24** | ❌ 回退 |
| **E2 split，关闭 MTP** | 36.0×10.2 = **368 ms** | 1 | **2.72** | ✅ +33% |
| **P0（embedding/lm_head 移出显存）+ MTP** | 718 ms | 2.04 | **2.84** | ✅ +39% |
| **P0 + E2 split，关闭 MTP** | 207 ms | 1 | **4.84** | ✅ +137% |

**判定**：E2 **不能用 MTP** —— CPU 内核是 ALU 受限（§1.2：ms/token 随 T 恒定），
MTP 摊薄的是访存而不是 ALU。方案文档 §4 的 "≈4.4 tok/s（MTP 同乘）" 不成立；
但**关闭 MTP 后 E2 自身有 +33%**，且与"减少 host 字节"（P0）**正交**。

## 8. 修正后的建议路线

### 优先序（P0/P1 已于 2026-09-17 上午执行完毕）

| # | 动作 | 状态 | 结果 |
|---|---|---|---|
| **P0** | 修 int8 参考实现的 2 个 bug（§6.3） | ✅ 完成 | 单链 `rel_l2 5.401e-03`（压线超标） |
| **P0** | 整数精度方案：激活 int8 **残差双链**（`x ≈ s₁q₁ + s₂q₂`） | ✅ 完成并验证 | `rel_l2 1.972e-05`，只贵 22% 带宽 |
| **P1** | 用修好的整数内核重测 T 扫描 | ✅ 完成 | ❌ ms/token **恒定** ⇒ 仍 ALU 受限，**不可与 MTP 相乘** |
| **P2** | 铺 E2 正式管线 | ⏸ **改变顺序** | 先做 P0'（embedding/lm_head 移出显存，与 MTP 正交），再做 E2 |

**结论修正**：整数路线**没有**解决 ALU 瓶颈（§6.1 的预期落空）。E2 的正确用法是**替代** PCIe，
而不是在其上**叠加** MTP。真正与 MTP 正交的杠杆是**减少每轮 host 字节数** —— 把 embedding + lm_head
（3.12 GB，恒驻留）移出显存预算，让 ratio 从 0.8 降到 ~0.56 ⇒ +44%，且 MTP 保留。
完整计划见 `rtx4060-27b-e2-cpu-gemv-decision-2026-09-17.md` §4。

**ALU 预算对比（为何整数路线是唯一出路）**：同一 32 个元素

| 路径 | 关键 uop | 说明 |
|---|---|---|
| fp32 精确 | ~16 个（8× `vpmovsxbd` 占 p5）+ 16 FP | p5 端口每 cycle 仅 1 条 → **p5 是硬瓶颈** |
| 整数 `maddubs`+`maddwd` | **2 个**（均在 p0/p1） | 差 **8×** |

### 明确不建议

- ❌ 用"把权重预展开成 1 字节/元素"来省 shuffle 开销：字节数翻倍（0.53→1.06 B/权重），把瓶颈从 ALU 换回访存，与 E2 初衷相反。
- ❌ 为凑 E2 而关掉 MTP：E2 单独 ≈ 持平，回退 2.22× 收益。

## 9. 若 P1 通过，E2 正式管线改造点（预登记）

在"访存受限内核"确认后再动，改造点已勘定：

| 层 | 位置 | 动作 |
|---|---|---|
| L1 | `linear.cpp` `dispatch_linear` | 入参**不带 residency**，需新增"host 常驻"判据分流到 CPU 内核 |
| L2 | plan + `.cu` | host 常驻权重不进 GPU 内核 |
| L3 | wrapper | 最易漏，需逐个核对 |
| L4 | workspace | CPU 路径不需要 GPU workspace |
| L5 | `weight_input.cpp` `prepare_linear_weight` | 权重本就常驻 host，无需上传 |

其它必需件：
- 新增 `cpu_gemv.cpp`，复用本轮已验证的 RowSplit 解码 + 预置换激活 + 双位序表；
- **跳过 `ensure_layer` 的上传**（host 常驻层不再流送）；
- 线程池集成：**必须用扁平抢单 + 单次栅栏**（§4.5），线程数取物理核数附近，**不要**直接取 `hardware_concurrency()`（20 线程挤 14 核会劣化）；
- 帧内调度：CPU GEMV 与 GPU attention 需并行流水（否则 CPU 计算期间 GPU 空转）；
- 与 MTP 的接口：确认 `model_instance.cpp:68` 的 P0 互斥在整数路线下可放开。
