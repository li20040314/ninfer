## 一、这事到底有多离谱 🤯

人人都说「本地跑大模型必须大显存」，27B 更是「24G 起步、没卡别想」。

我手上是台 RTX 4060 Laptop：**8GB 显存（本机实测 8188 MiB）、i9-13900H + 32GB DDR5 双通道**。

结果👇（本机实测）

- **9B 模型满血直跑**：decode **38.2 tok/s**、prefill 201 tok/s，权重 5.28GiB 全装显存。
- **27B 模型 CPU offload**：基线 0.9 tok/s → 接 MTP 投机后 **2.0 tok/s**、中文输出正确，显存只占 4.31GiB。
- 全程基于开源推理引擎 **NInfer** 做本地化改写适配，不是 llama.cpp 那类开箱即用框架。

这不是开箱即用的现成框架，而是在开源 NInfer 之上，从算子层把一套为 5090 调优的引擎，逐层改写适配到 NVIDIA Ada Lovelace 架构。

## 二、先过五道门：移植一个模型，不是改一处 🚪

最容易踩的认知坑：以为「加个模型配置就能跑」。实测要同时过 **五层闭表**（L1–L5），只看 `linear_dispatch.cpp` 会严重低估工作量。

| 层 | 位置 | 形态 | 改法 |
|---|---|---|---|
| L1 | `ops/linear/<fmt>/` | `ShapeEntry` 闭表 + 选择器 | 新增表项（机械但多） |
| L2 | `ops/<op>/*_plan.cpp` 及 `.cu` | 硬编码「精确问题」元组 + **内核里烤死的几何** | 改谓词 + 参数化内核 |
| L3 | `ops/wrapper/*.cpp` | 公共 op API 里另有一整套写死的 n/k/rows | 加分支（**最易漏**） |
| L4 | 跨层常量 | 工作区容量、stride | 替换常量 |
| L5 | `ops/weight_input.cpp` | 权重准备期的独立闭表 | 加分支 |

好消息：约束全部收敛在 `src/ops/`，`models/`、`core/`、`runtime/`、`serve/` 零硬编码模型几何 —— 符合架构分层意图。

## 三、9B 满血：38 tok/s 是怎么拿到的 ⚡

Qwen3.5-9B 的 hidden=4096（27B 是 5120），所有量化闭表里 **一个 (n,k) 都没有**。

**关键判断**：纯文本、不带 MTP/vision 就能跑，只需 Q4/Q5/Q6 —— 这是最短可用路径。

走过的坑（都是会真实咬人的那种）：

- **注意力几何闭表**：9B 是 `(16,4)`，和 35B 的 `q_heads=16` 撞车，所有按 query_heads 的二分支必须改用 **kv_heads** 区分。
- **i8 内核 warp 整除性**：GroupSize=4 让原 warp 配置全部失配，要重排成 16/8/4 三档。
- **判据伪超标**：`linear_swiglu` q4 的 9B `rel_l2=3.34e-3` 超 3.3e-3 上限 1.3% —— 不是代码 bug，是 bf16 中间结果的「误差地板」依赖数据分布。给 fp64 oracle 加「模拟 Materialized」模式后证明确实逐位最优，判据放宽到 3.7e-3（保留 2× 余量，不损失检测力）。
- **合作启动崩溃**（真移植 bug）：`cooperative_resident_ctas_per_sm()` 返回的是 5090 上标定的编译期常量，4060 每 SM 只有 1536 线程 → `cudaErrorCooperativeLaunchTooLarge`。修法：上界 + 运行时占用率 API `min()`。

**验收（9-16 晚）**：decode 38.2 tok/s、权重 5.28/5.28 GiB、12 套件回归 11/12（唯一 FAIL 是 27B 已知的 fp32 累积地板，故意遗留）。

## 四、27B 装不进 8G？那就把权重放内存 💾

27B 权重转换产物 **17.1GB**（原始 safetensors 共 51.75GB），8GB 显存根本装不下。一个必须先对齐的概念：

> NInfer 全部算子是 CUDA kernel，**没有 CPU 计算路径**。「部分放 CPU」在本引擎的可行语义是 **权重驻留主机内存 + 数据仍由 GPU 计算**（每 token 把该层权重经 PCIe 拷入显存槽位后执行）。

![offload 流送示意](images/offload.png)

**两个被 9B 掩盖的 P0 坑**（9B 显存恰好挤过去，27B 直接 free=0）：

1. **槽位改层内轮转**：原槽位 = 全部流送字节 → GPU 仍要装全量。改为槽位 = **最大单层足迹**（≈0.21GiB），`ensure_layer()` 覆盖写。
2. **ratio 语义翻转**：原 `ratio` = 「驻留 GPU 的比例」，和用户语义相反。改为 `ratio` = **流送到 host 的比例**：`target_resident = (1-ratio) × layer_bytes`。`--offload-ratio 0.9` → GPU 驻留 3.99GiB。

另：embedding+lm_head（bf16，≈3.1GB）**不参与 offload、恒驻留** —— 这决定了 27B 实际可用比例 **≥0.9**。

**验收（0.9）**：GPU 3.99GiB / host 11.94GiB / decode **0.9 tok/s** / 中文正确「我是通义千问……」。

## 五、从 0.9 到 2.0：提速三连击 🚀

瓶颈定位先摆数据：**每 token 流送 ≈14.5GB，有效 PCIe ≈13GB/s，传输占每 token 时间 98% 以上**。一切不减少流送字节、或不绕开 PCIe 的优化，收益上限都很低。

### ▍第一击：量化降 bit + 双槽（A+B）
把 down/output 从 Q5 降到 Q4（受配对合同约束：attention/value、gate 不能降 Q4），并改双槽轮转。
- 0.9 → **1.0 tok/s**（+11%），产物 17.11 → 16.14GB（−5.7%）。

### ▍第二击：MTP 投机解码（F1，×2.22）
27B/9B 都有 `mtp_num_hidden_layers=1`（按旧字段名 `num_nextn_predict_layers` 搜会误判「无 MTP」）。放宽 `model_instance.cpp` 的保守互斥，放行 MTP、仍禁 dflash。
- k=3 是甜点（k=5 无增益，草稿越深接受率越低）。
- 0.9 → **2.0 tok/s（×2.22）**，GPU 4.31GiB，输出与基线 219/222 字符一致。
- **核心认知**：MTP 不减少任何 PCIe 字节，只是让同一批字节服务更多 token —— 「传输摊薄」才是正解。

### ▍第三击：embedding 移出显存（P0-b，实测 +11.1%）
embedding 是稀疏行 gather（每步只读 T 行），实测 **pinned host 直读甚至比 device 略快**（8.51 vs 9.47 μs），且 zero-copy 不破坏 CUDA Graph。把 1.258GiB 腾出还给层后：
- decode **1.8 → 2.0 tok/s（+11.1%）**，GPU 权重 4.31 → 4.22 GiB。
- prefill +32.7%（提示词短、噪声大，**仅供参考**）。
> 这一步只动了 embedding。决策文档推算：若把 lm_head（也是 1.258GiB）一并移出显存预算，可让 ratio 0.8→0.56，**再 +44%（约 2.9 tok/s）**，且仍保留 MTP —— 属 Phase 2 待交付项。

## 六、最硬核的一课：先量地板，再铺管线 📏

原方案文档给 E2（CPU GEMV 混合计算）的预期是「PCIe 13GB/s → DDR5 55GB/s，E2 + MTP 同乘 ≈4.4 tok/s」。

我们没急着铺管线，先用一个独立微基准量了地板：

| 路径 | 带宽 | 结论 |
|---|---|---|
| 内存流式读上限 | 63.6–67.8 GB/s | ≈ PCIe 的 **5×**（前提成立） |
| 精确 fp32 CPU GEMV | 33.6 GB/s，rel_l2 3.4e-7 | 数值达标，但 **ALU 受限** |
| int8 split 双链 | 35.4 GB/s，rel_l2 2.0e-5 | 只贵 22% 带宽，达标 |

决定性发现：**fp32 路径 ms/token 随 T 恒定**（总耗时 = T×常数）→ 纯 ALU 受限。MTP 摊薄的是「访存」而不是「ALU」，所以 **E2 与 MTP 不可相乘**（实测 E2+MTP = 1.2 tok/s，反而回退）。

量地板这一步，拦下了一条会耗掉大量工期但**产出为零**的管线改造。修正后的路线：

- E2 split 单独（关 MTP）：**2.72 tok/s（+33%）**
- 先把 embedding+lm_head 移出显存预算（与 MTP 正交，决策推算 **+44%**）：约 **2.9 tok/s**（实测推算 2.84，+39% vs 现状 2.04）
- 二者叠加（Phase 3）：预期 **~4.84 tok/s（+137%）**

> 注：「+44%」是「embedding+lm_head 全移出显存」对 ratio 的降幅推算（详见第三击）；上表是逐条实测/推算的 tok/s，避免与 2.84 错配。

**Phase 1 已交付**：CPU RowSplit GEMM 内核（AVX2 + 标量参考）接线完成，t=1 实测 **29~72 GB/s（2.2~5.5× PCIe）**，端到端一致性验证通过。
